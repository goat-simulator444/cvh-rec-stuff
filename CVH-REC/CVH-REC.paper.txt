CVH-REC: A novel method for web API
recommendation based on cross-view HGNNs
Shanquan Gao, Yihui Wang, Zhenwei Ou
Abstract—With the advancement of service computing technology, software developers tend to consume one or more web APIs, a
practice that helps them avoid the behavior of reinventing the wheel. These web APIs are capable of providing services or data on the
Internet; developers can use them to create feature-rich mashups. Against this backdrop, the number of web APIs across various
platforms is growing rapidly, making it increasingly challenging to identify suitable ones for upcoming mashup creation. Consequently,
web API recommendation has emerged as an effective means to facilitate web API discovery. We have proposed a novel web API
recommendation method called R2API, which constructs the interactions between mashups and web APIs, as well as their tag usage
records, into multiple homogeneous hypergraphs and then adopts HGNNs with multi-task learning to learn entity vectors for the
recommendation task. While the result is encouraging, R2API’s limitation is its use of simple homogeneous hypergraphs to describe
entities, failing to characterize them comprehensively and accurately. To further enhance recommendation performance, this work
proposes a novel cross-view HGNNs-based web API recommendation method, namely CVH-REC. First, CVH-REC models the
interactions between mashups and web APIs, as well as their tag usage records, into a multi-view knowledge graph to characterize
entities more comprehensively and accurately. This knowledge graph comprises a global main hypergraph and four sub-hypergraphs
from local views. Second, CVH-REC adopts a contrastive learning and multi-task learning framework to drive multiple HGNNs in jointly
learning entity vectors. Third, CVH-REC leverages the SBERT model to derive the semantic vector from the mashup requirement and
transfers it into the vector space of the knowledge graph with an MLP. This process enables the generation of a higher-quality
requirement vector. By comparing the vector of the mashup requirement with those of web APIs, CVH-REC generates a
recommendation list for mashup creation. Extensive experiments on a real-world dataset demonstrate that the proposed method
outperforms baseline methods.
Index Terms—Multi-view knowledge graph, cross-view HGNNs, contrastive learning, multi-task learning, web API recommendation.

I NTRODUCTION

Given the ever-evolving business demands in the consumer
market, companies must iterate rapidly during software development and shorten the development cycle. This allows
them to meet consumers’ business needs with maximum
efficiency [1]. Against this backdrop, a growing number of
software developers are turning their attention to mashup
application, which is implemented by combining one or
more web APIs that can provide services or data on the
Internet [1], [2], [3]. With the explosive growth of web
APIs, developers often struggle to efficiently identify the
web APIs that meet their requirements [4], [5], [6]. As a result, web API recommendation has emerged as an effective
means to facilitate web API discovery [7].
The web API recommendation methods are usually classified into two main categories: content-based methods and
CF (collaborative filtering)-based methods [8]. The core logic
of content-based methods is to recommend web APIs by
matching requirement texts against the textual descriptions
of web APIs. Nevertheless, because of the semantic gap
between different data types, their performance remains
unsatisfactory [9]. In contrast, CF-based methods handle
mashup requirements by first identifying existing mashups
with high similarity to the mashup requirement, and then

recommendation list and presents it to software developers.

P ROBLEM DEFINITION AND PRELIMINARIES

To better describe the web API recommendation method
proposed in this paper, we present the problem definition
and preliminary concepts in this section.
2.1

Problem definition

A mashup consists of a textual description, a set of web
APIs employed by it, and a set of tags associated with it. A
web API consists of a textual description, a set of mashups
that employ it, and a set of tags associated with it. Mashup
tags typically describe the functions that mashups provide
to users, while web API tags describe the support web APIs
offer for mashup creation or the capabilities they provide to
users. Some overlap exists between the two types of tags.
A mashup requirement is a textual document representing
a requirement for mashup creation. Typically, it describes
the functions of the mashup to be created. Based on the
interactions between mashups and web APIs in historical
data, as well as their tag usage records, we define web API
recommendation as selecting and suggesting a suitable set
of web APIs for the mashup requirement. Specifically, web
APIs recommended for a given mashup requirement should
have a high probability of being adopted, while minimizing
the likelihood that developers will utilize web APIs not
included in the recommendation.
2.2

Preliminaries

We introduce the important preliminary concepts that underpin our proposed method, including three key concepts: HGNNs, contrastive learning, and multi-task learning. These form the essential background for understanding
our method.
HGNNs. Hypergraphs, in contrast to ordinary graphs,
are distinguished by their ability to connect multiple entities
via a single hyperedge [18], [19]. This unique property
enables hypergraphs to effectively represent complex multidimensional relationships. HGNNs are deep learning models based on hypergraph structures. They facilitate information transmission and aggregation across multiple entities
through the bidirectional message-passing mechanism. That
is, each hyperedge aggregates the features of all entities
it connects to form the global information of that hyperedge; subsequently, each entity aggregates information from
the hyperedges it is connected to, thereby updating its
own features. Compared with traditional GNNs, which can
only handle pairwise relationships, HGNNs can directly
model interactions between multiple entities connected by

Contrastive learning. The core role of contrastive learning lies in guiding models to learn more essential and
robust feature representations by constructing relationships
of similarity and dissimilarity between samples [20]. Contrastive learning does not rely on large amounts of labeled

data; instead, it designs positive and negative sample pairs,
enabling models to learn to shorten the feature distance
between positive samples and lengthen that between negative samples during training. This mechanism not only
helps models mine core semantics from data and enhance its
anti-interference ability against noise, but also alleviates the
problem of sparse supervision signals, allowing models to
exhibit stronger generalization ability in downstream tasks
such as classification, retrieval, and recommendation [21].
Multi-task learning. Multi-task learning is a machine
learning paradigm that enables the model to learn multiple
related tasks simultaneously [22], [23]. Its core lies in allowing knowledge transfer and complementation between
different tasks through sharing the model structure, thereby
improving the overall learning effect. The role of multi-task
learning is mainly reflected in two aspects: for tasks with
scarce data, it can enhance feature learning by leveraging
the rich data from related tasks; at the same time, the
constraints between multiple tasks can reduce the risk of
overfitting and improve the model’s adaptability to complex scenarios. Ultimately, multi-task learning enables the
model to perform better on multiple tasks than single-task
models trained independently, and is particularly suitable
for scenarios where tasks are closely related.

P ROPOSED M ETHOD

In this section, we present the proposed CVH-REC. CVHREC involves three main steps: first, building the multiview knowledge graph; second, learning entity vectors via
this knowledge graph; third, recommending web APIs for
specific requirements.
3.1

Building the multi-view knowledge graph

As shown in Fig.1, CVH-REC models the interactions between mashups and web APIs in historical data, along with
their tag usage records, into a multi-view knowledge graph.
The knowledge graph comprises a global main hypergraph
and four sub-hypergraphs from local views. The main hypergraph M includes all types of entities (i.e., mashups,
web APIs, mashup tags, and web API tags) and records
interactions between them. It uses a hyperedge to connect
each entity to those with which it interacts, with the connection weights between entities and hyperedges in the main
hypergraph all set to 1.

The four sub-hypergraphs are homogeneous hypergraphs constructed for mashups and web APIs from two
local views: behavioral similarity and semantic similarity.
Each entity in the sub-hypergraph is connected to its similar entities via a hyperedge. Behavioral similarity means
that mashups employ similar web APIs or web APIs are
employed by similar mashups; semantic similarity refers
to mashups or web APIs having similar tags. Behavioral
similarity reflects the practical functional correlations between entities of the same type—specifically, which web
APIs are commonly employed together by mashups or
which mashups share similar web API usage behaviors.
This makes it a key signal for recommendation, as developers’ web API selection is inherently driven by functional
requirements. Meanwhile, semantic similarity supplements
the correlations between entities of the same type with
conceptual relevance, forming a complementary framework
with behavioral similarity.
Specifically, there are the mashup behavioral similarity sub-hypergraph S1, mashup semantic similarity
sub-hypergraph S2, web API behavioral similarity subhypergraph S3, and web API semantic similarity subhypergraph S4. When constructing a sub-hypergraph, CVHREC calculates the similarity scores between each entity and
the other entities in the sub-hypergraph; the entities with a
similarity score greater than or equal to the hyperparameter
are regarded as its similar entities. The hyperparameters
of sub-hypergraphs S1, S2, S3, and S4 are α1, α2, α3, and
α4, respectively. The similarity scores between an entity
and its similar entities are used as the connection weights
between the corresponding hyperedge and these entities.

3.2 Learning entity vectors via the multi-view knowledge graph
After constructing the knowledge graph, CVH-REC utilizes
a dedicated HGNN for each hypergraph to learn the vectors
of entities within it. As shown in Fig. 3, CVH-REC calculates
the weighted average of the vectors learned by each mashup
or web API from the two sub-hypergraphs as its local vector.
Each sub-hypergraph is configured with a trainable weight.
The final vector of each mashup or web API is the weighted
average of its local vector and its global vector learned from
the main hypergraph. CVH-REC configures two trainable
weights for local information and global information.
During the training phase, CVH-REC leverages a contrastive learning and multi-task learning framework to drive
the adjustment of model parameters. Contrastive learning
can enhance the quality of entity vectors by enabling entity
vectors to focus on core semantics, aligning vector spaces
across views, and alleviating the issue of sparse supervision
signals. The contrastive learning includes two local contrastive learning tasks and two global contrastive learning
tasks: the local contrastive learning task of mashups, the
local contrastive learning task of web APIs, the global contrastive learning task of mashups, and the global contrastive
learning task of web APIs. Local contrastive learning tasks
enhance the consistency and complementarity of information between sub-hypergraphs by aligning the vectors of
the same entity in different sub-hypergraphs, thereby improving the robustness of local features; global contrastive
learning tasks avoid the separation of local information from
global semantics by correlating the local vectors and global
vectors of entities, enabling the final vectors to incorporate

both fine-grained details and overall associations.
Before completing the contrastive learning tasks, CVHREC adopts MLPs to map the original vectors into the
contrastive spaces. The MLP acts as a cross-view semantic
translator in this process: it eliminates the spatial heterogeneity of the original vectors through non-linear mapping
and constructs a semantically consistent contrastive space
where the contrastive loss can accurately capture the semantic similarity between entities. Each contrastive learning task
is configured with an MLP, and each MLP consists of three
layers: an input layer, a hidden layer, and an output layer.

Similar to our previous work [15], HGNNs in CVH-REC
do not obtain the initial entity vectors based on random
vectors. Instead, CVH-REC assigns a semantic vector to
each entity, and HGNNs adjust these semantic vectors to
obtain the initial entity vectors during model training. The
semantic vectors of entities inherently encode the domainspecific knowledge, and assigning them to entities enables
HGNNs to leverage this prior knowledge during message
passing. Benefiting from this point, the learned final entity vectors not only capture the structured knowledge of
the knowledge graph, but also retain the domain-specific
knowledge. Specifically, for each mashup or web API, CVHREC uses SBERT to generate a vector for each sentence
in its textual description, then takes the average of these
vectors as its semantic vector. For each tag entity, CVH-REC
directly generates a vector for the tag itself using SBERT,
which serves as its semantic vector. Since the initial vectors
of entities are derived from the semantic vectors output
by SBERT, the final vectors of entities obtained by HGNNs
have the same dimension as these semantic vectors, i.e., 768dimensional.
3.3

Recommending web APIs for specific requirements

When dealing with a specific mashup requirement, CVHREC leverages SBERT to process it, obtaining its semantic
vector. However, instead of directly using this semantic
vector as the final vector of the mashup requirement, CVHREC transfers it into the vector space of the knowledge
graph. This transfer integrates semantic information with
the knowledge graph’s structured knowledge, thereby facilitating the learning of a more comprehensive and precise
requirement vector.

Dataset and Experiment Setup

Our experiments used an open-source dataset crawled from
ProgrammableWeb by Liu et al. [24], which contains 7,947
mashups, 1,693 web APIs, and 16,200 interaction relationships. We then performed data cleaning to filter out mashup
and web API entities lacking metadata (e.g., textual descriptions, tags, and mashup-web API interaction records),
yielding the final experimental dataset (see Table 1).
We used ten-fold cross-validation to evaluate the performance of CVH-REC. First, we randomly divided the
mashups in the experimental dataset into a validation set
and a main dataset, comprising 10% and 90%, respectively.
Second, we randomly split the main dataset equally into ten
sets: nine served as historical data, and the remaining one
as the test set. This process was repeated ten times to ensure
each set was used as the test set exactly once. Third, we
trained the parameters in CVH-REC using historical data.
The hyperparameters were selected based on the validation
set, specifically choosing the settings that performed best
on it. The specific selections of key hyperparameters and
model details are shown in Table 2. Finally, we treated the
textual descriptions of mashups in the test set as mashup
requirements and used CVH-REC to generate a list of web
APIs for each requirement. By comparing the recommended
web APIs with those actually used by the mashups, we
evaluated the performance of CVH-REC. In addition, details
about the testbed are also presented in Table 2.

Table 4 presents the experimental results of CVH-REC and
all baseline methods. In terms of Precision, Recall, MAP,

which highlights that this performance improvement has
important practical significance for the web API recommendation task. Our analysis identifies three reasons for CVHRe’s superior recommendation performance over R2API.

low-frequency web APIs achieve a significantly lower success rate than high-frequency web APIs. Third, we assessed
the performance of CVH-REC by comparing the web APIs it
recommended against those actually employed in mashups.

4.6 RQ3: Impact of contrastive learning, global contrastive learning, and local contrastive learning
In the learning phase of the knowledge graph, CVH-REC
employs a contrastive learning and multi-task learning
framework to drive multiple HGNNs in jointly learning entity vectors. In RQ3, we conducted an experiment to analyze
whether contrastive learning, global contrastive learning,
and local contrastive learning exert a positive impact on the
performance of CVH-REC. To this end, we first constructed
three variants of CVH-REC, namely CVH-REC-contrastive ,
CVH-REC-globalContrastive , and CVH-REC-localContrastive . Unlike
the variants in RQ2, which remove sub-hypergraphs, the
variants in this RQ retain hypergraphs from all views; they
only remove the contrastive learning tasks between different
hypergraphs. Specifically, CVH-REC-contrastive does not consider any contrastive learning tasks; CVH-REC-globalContrastive
does not consider global contrastive learning tasks; and
CVH-REC-localContrastive does not consider local contrastive
learning tasks. We then evaluated the impact of contrastive
learning, global contrastive learning, and local contrastive
learning by comparing the experimental results of variants
and CVH-REC.

integrating contrastive learning enhances the recommendation performance of CVH-REC. Our analysis identifies

semantics, filtering out noise and redundant information.

Threats to Validity

Threats to construct validity. In our work, a potential
construct threat arose from the correctness of the evaluation metrics. To mitigate this risk, we employed standard
metrics—Precision, Recall, MAP, and NDCG. These metrics
have been extensively used in prior studies on web API
recommendation.
Another potential threat to construct validity stems from
the choice of statistical metric: specifically, we adopted the
mean rather than the median of the evaluation results across
all mashup requirements. Compared to the median (a robust
measure of central tendency that is insensitive to extreme
values), the mean is more sensitive to the performance differences across all test cases—especially the improvements
in the scenarios where the baseline methods underperform.
This characteristic makes the mean a more suitable metric
for quantifying the overall performance gains of CVH-REC
over the baseline methods.
Threats to internal validity. A potential threat arose
from the way we evaluated the performance of recom-

we included a variety of baseline methods covering both
traditional and recent state-of-the-art methods. Specifically,
we adopted the popularity-based method POP, which is
commonly used as a basic baseline in many studies, and also
selected recent methods published in high-impact conferences and journals. These representative baselines ensured
a fair and meaningful comparison.

R ELATED WORK

This section introduces works related to web API recommendation, including content-based, CF-based, and deep
learning-based methods.
5.1

Content-Based Methods

Content-based methods assist developers in discovering
suitable web APIs by analyzing the semantic relationships
between requirement texts and the textual descriptions of
web APIs. Li et al. [32] employ probabilistic modeling to
uncover latent topic structures in requirement documents

14

and web API descriptions, enabling semantic similarity
computation and estimation of mashup–API matching. Shi
et al. [9] present a tag-attention Siamese BiLSTM model for
web API recommendation that jointly embeds web APIs
and mashup requirements, using tags of web API to guide
attention to functionally relevant words. Zhao et al. [33]
combine multiple types of features including textual, nearest
neighbor, API-specific, and tag features to estimate the relevance between mashup requirements and web APIs using a
regression model. Zhong et al. [34] generate comprehensive
web API representations from usage history to bridge the
vocabulary gap between mashup developers and web API
providers. By leveraging the Author-Topic Model to capture
web API-word co-occurrences, these representations can be
dynamically refined and enriched. Sang et al. [35] propose
SAMF, a model that combines Bayesian matrix factorization
with Doc2Vec to mine the semantics of mashup and web
API descriptions. Text similarity and adversarial training
are incorporated to alleviate data sparsity and enhance
recommendation accuracy and robustness. However, the
performance of content-based methods is often hindered
by the semantic gap between requirement texts and web
API descriptions, including both the vocabulary gap and
the intention gap. This makes it difficult for these methods
to accurately align developer needs with appropriate web
APIs.
5.2

Collaborative Filtering-Based Methods

Collaborative filtering (CF) has been extensively utilized in
web API recommendation tasks [36], [37]. CF-based methods recommend web APIs to a mashup requirement by
identifying its similar mashups from historical data and
generating the list of web APIs based on the web APIs
employed by these mashups. Rahman et al. [38] introduce a
user-based collaborative filtering method for web API recommendation, which leverages a two-level topic model to
discover mashups that are similar to the requirement. Xiong
et al. [39] combine collaborative filtering and textual content
to integrate the invocation interactions between mashups
and web APIs and their functional descriptions through
neural networks. Yao et al. [40], [41] propose a probabilistic
matrix factorization model enhanced with implicit correlation regularization, aiming to improve the quality of web
API recommendation while promoting greater diversity in
the recommended results. Fletcher et al. [42] incorporate
the implicit user preferences (i.e., invocation history) into
the matrix factorization model to improve the accuracy
and diversity of recommendations. Despite the remarkable
success achieved by many CF-based methods, they are often
susceptible to the popularity bias.
5.3

With the advancement of deep learning across various
domains, many recent studies adopt them to address the
problem of web API recommendation. Fan et al. [27] present
GSR, a seq2seq-based web API recommendation model
that leverages reinforcement learning to handle sequence
dependency. Xiao et al. [43] propose a novel group feature aggregation web API recommendation framework that

C ONCLUSION AND F UTURE WORK

This work proposes a novel web API recommendation
method, i.e., CVH-REC, which involves three main steps.
First, CVH-REC models the interactions between mashups
and web APIs, as well as their tag usage records, as a
multi-view knowledge graph to comprehensively and accurately characterize entities. Second, CVH-REC adopts a
contrastive learning and multi-task learning framework to
drive multiple HGNNs in jointly learning entity vectors.
Third, CVH-REC obtains the semantic vector of the mashup
requirement using the SBERT model and transfers it into
the vector space of the knowledge graph with an MLP.
CVH-REC generates a recommendation list of web APIs by
comparing the vector of the mashup requirement with those
of web APIs. Through a series of research questions and
experiments, we verified that CVH-REC performs better
than the baseline methods.
In future work, we aim to generate explanatory texts for
web API recommendation lists, thereby helping software
developers better understand and utilize the recommended
web APIs. The robust text generation capabilities of LLMs
hold promise for achieving this objective.
